The feature records administrator-confirmed external collections and refunds. It does not execute payments or verify a payment provider. Clerical corrections preserve the original entry and do not count as refunds. See the [backend contract](order-payments-backend.md) and [public summary contract](order-payment-public-frontend.md).

The browser scenarios in `e2e/order-payments.spec.mjs` use the real disposable local API, synthetic orders, one worker and no retries. A network guard rejects nonlocal browser writes. Private runtime credentials are read only inside the test process; automatic screenshots and traces are disabled. Explicit screenshots contain only synthetic order/payment data after login. Cleanup checks the synthetic customer marker before cancelling its order.

The first scenario covers explicit review before recording, invoice preservation, a partial bank collection before shipping is confirmed, agreed shipping, receipt refresh, private-reference exclusion, and a committed cash collection whose HTTP response is deliberately lost. Reloading the admin page must retain the original attempt identity; a keyed read recovers the exact entry without another POST. It then records a real refund, separately corrects an erroneous original collection, and records the corrected amount using the same external reference. Every original entry remains in history. Cancellation suppresses debt/credit claims, does not invent a refund, and permits recording an externally completed refund afterward.

The second scenario blocks a POST before it reaches the API. A negative keyed read must keep the form locked and allow only retrying the exact original body/key. A real concurrent collection then invalidates a reviewed draft: the first attempt receives 409, explicit recovery loads the current ledger, and a fresh attestation/review uses the new revision without losing the draft.

The third scenario combines uncertainty with a later successful collection from another session. The original attempt's exact retry must return the server's bound-request terminal proof, preserve the draft across reload, and require explicit recovery and fresh attestation/review. It verifies that a new key uses the current revision and creates exactly one intended entry, resolving the formerly permanent lock without duplicating a collection. Unit and backend race tests cover the corresponding correction flow and distinguish this proof from an ordinary negative read or generic conflict.

Amounts in these scenarios are synthetic test data, not product costs, merchant payment policies or proof of a real money movement. The source includes desktop/mobile overflow checks and explicit admin/receipt screenshots. Backend tests separately cover ownership, role restrictions, duplicate references, malformed requests, safe exact arithmetic, concurrent refunds/corrections, legacy null fields and atomic invoice/status checks.
