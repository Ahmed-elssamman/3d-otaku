## Architecture and baseline

- Express 4, ESM JavaScript, Mongoose/MongoDB, bcrypt, JWT access/refresh tokens, local filesystem media storage.
- Public catalog, account authentication, guest/customer orders, custom requests/contact submissions, administrator product/order/request/settings endpoints are present.
- The initial backend had no automated tests or syntax-check scripts, no local MongoDB runtime, no `.env`, and no production deployment/runbook.
- Initial `npm ci`/`npm audit` reported four vulnerable packages, including high-severity Multer denial of service advisories. Compatible lockfile updates now produce **zero reported production vulnerabilities**.
- The frontend actually uses Angular 21, while the supplied workspace rules describe Angular 19. Existing framework versions were preserved.

## Frontend contract

- `POST /api/orders/quote` returns `quoteVersion: 2`, exact current EGP line/shipping totals, captured configurations and quote/configuration fingerprints without writing business records. New `POST /api/orders` inserts require `items: [{ productId, quantity }]`, customer details, `expectedQuoteFingerprint` and `expectedQuoteVersion: 2`; the storefront always sends `Idempotency-Key`. Committed legacy requests and approved version 1 decisions remain exactly recoverable. Public Order lines preserve configuration or explicitly return null for legacy history; only protected administrator detail exposes manufacturing snapshots.
- Customer requires `fullName`, Egyptian mobile (`phone` or `whatsappNumber`), `city`, and `address`. Optional `country` must be `EG`; optional email is validated. Egyptian international/local formats and Arabic digits are normalized.
- Create returns the complete server invoice plus `trackingToken`, `deliveryFeeConfirmed`, `estimatedDeliveryDays`, `statusHistory` and `customer.country`.
- Keep the same checkout key and saved original payload while resolving an uncertain submission. A 409 containing `errors.checkoutSession` means restore the original sign-in state or contact the store; `errors.checkoutDetails` means restore the original details to recover the receipt. Neither response authorizes a new attempt or discloses the existing receipt. See [checkout idempotency](checkout-idempotency.md).
- Only an exact `checkoutNotRecorded` response proves the matching durable rejected attempt cannot insert. It permits fresh quote review, explicit customer confirmation and a new key. Generic 409/422 on an already uncertain retry retains the original body/key. Drain all pre-reservation writers before rollout and never reset/expire bindings; see [durability and recovery boundary](checkout-pricing.md).
- `GET /api/orders` is authenticated. `GET /api/orders/track/:orderNumber` accepts authenticated ownership or `X-Order-Token`; the capability must never enter the API URL path/query. Browser-only private-link integration and the tracking no-store policy are described in the [guest tracking contract](guest-tracking-backend.md).
- `POST /api/auth/refresh-token` rotates **both** tokens. The frontend must save both returned values.
- Public/custom/admin request records include string `id`. Product model types include STL/OBJ/PLY.
- Anonymous guest orders remain tied to their receipt token. They are not linked to an account merely because its email/phone matches; that would expose private orders.

## Local commands and isolation

Run from `outako/backend-api`:

```powershell
npm ci
npm run check
npm test
npm audit --omit=dev
npm run dev:local
```

`dev:local` runs the API at `http://localhost:4000/api` with a disposable local MongoDB process. It reads a public deployed catalog/settings snapshot, preserves product IDs, and caches allowlisted public media locally. It does not access private production data. Test orders/accounts are written only to the disposable database. Prices/content in this snapshot are existing integration fixtures, not a release-approved catalog.

Proxy both `/api` and `/uploads` from Angular to `http://localhost:4000`. A randomly generated test administrator and local database URI are stored in ignored `.local/runtime.json`; do not commit or publish this file. `src/uploads/local-snapshot/` is also ignored. The first setup downloads the MongoDB binary (approximately 819 MB on Windows); following runs reuse it.

For a normal persistent backend, configure `.env` and run `npm start`. Required production inputs: `MONGODB_URI`, distinct random `JWT_SECRET`/`JWT_REFRESH_SECRET`, deployed `CORS_ORIGINS`, correct `UPLOAD_BASE_URL`, and explicit `TRUSTED_PROXY_ADDRESSES` for the actual edge/SSR egress addresses when proxies forward client identity. An empty list trusts nobody. Numeric-hop configuration is being replaced: blank legacy values behave as absent and `TRUST_PROXY_HOPS=0` remains accepted; nonzero or malformed values fail with migration guidance. This new address contract passed the full 217-case suite and is active locally with an explicitly empty allowlist; see [proxy trust](backend-proxy-trust.md). Optional bootstrap credentials are `SEED_ADMIN_EMAIL` and a unique `SEED_ADMIN_PASSWORD` of at least 16 characters. Remove bootstrap credentials after provisioning. Keep the JWT access signing secret stable for existing guest tracking receipts, which use a keyed HMAC.
