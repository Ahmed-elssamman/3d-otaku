# Egyptian storefront implementation checkpoint

Updated 17 September 2026. The full user goal remains active. This checkpoint records substantial verified progress, not approval for production sales or a claim of permanent 100 scores.

## Implemented

The storefront now has Arabic RTL home, header/search, catalog, product cards, details, cart/guest checkout, receipts, orders, login/register, about, contact/custom-request and not-found pages. Warm off-white surfaces, dark green text and restrained green actions replace the animated red/purple public sections. The UI uses existing standalone components, external templates/styles, signals, typed contracts, companion data files and logical direction properties.

Product search is debounced, cancels obsolete requests, synchronizes URL filters and respects browser history. Product images link directly to details. Adding a product keeps the customer browsing and provides an explicit cart link. Interactive 3D loads only when requested. Product loading reserves viewport space. Arabic fonts are self-hosted as two full Arabic subsets; Latin uses system fonts.

The frontend now reaches a local real API through same-origin proxies. Production environment replacement is configured. PrimeNG 22 was incompatible with installed Angular 21 and required a different license; the project now uses the verified MIT community PrimeNG 21.1.10 line. Its theme initializes on the lazy admin route rather than loading in the storefront bundle. PrimeIcons is pinned to MIT 7.0.0. Its reproducible WOFF2 subset retains all 54 required glyphs, while `pi-spin` remains a CSS helper. Scanning the application and 262 PrimeNG runtime files, pinned upstream mappings and reviewed dynamic bindings prevents silently dropping a required icon. The font body is 9,568 bytes instead of 35,148, a 25,580-byte reduction (72.78%). Upstream CSS mappings, helpers, fallback references and license are retained; every build verifies coverage. The Angular favicon has been replaced with the storefront's existing green box symbol. Content-hashed icon fonts receive immutable caching in the preview; ordinary unversioned assets retain their shorter lifetime.

Orders use server-authoritative EGP prices and integer money arithmetic, Egyptian address/mobile validation, idempotency keys, private guest tracking and protected customer history. Checkout accepts guests, preserves drafts, clearly separates shipping estimates and payment confirmation, and displays the actual server receipt. Auth refresh rotation, upload validation, administrative product editing and server pagination have been repaired.

Administrative order, custom-request and contact-message screens now use real paginated/searchable APIs, current details, allowed status changes and explicit save confirmation. Optimistic state checks prevent one administrator from silently overwriting another. Customer-facing order notes and internal custom-request notes are clearly separated. Dashboard counts come from the database; missing metrics are not fabricated as zero. Orders preserve governorate and city separately.

Per-order shipping confirmation is now implemented through a protected API and a separate admin editor. The operator enters an agreed fee (including zero), confirms customer agreement and reviews the calculated invoice before saving. Integer-piastre arithmetic preserves item prices, subtotal and discount. Revision/status checks, idempotent requests and guarded legacy-field initialization protect concurrent writes; private shipping history records previous/new amounts and the operator. The UI retains stale or uncertain drafts and requires an explicit reload/review. Guest receipts and account orders display the current confirmed fee/total without exposing private notes. Shipping remains separate from payment and fulfillment status. See the [API contract](order-shipping-backend.md), [frontend behavior](order-shipping-frontend.md) and [browser evidence](order-shipping-qa.md).

Orders now also have an append-only record of administrator-confirmed external collections and refunds. A separate clerical correction preserves the original entry and never fabricates a refund. Exact piastre arithmetic, invoice/status/revision checks, duplicate-reference protection and keyed recovery prevent accidental duplicate recording. The admin page retains an unresolved action across reloads, permits only its exact retry after a negative read, and keeps shipping/payment/status operations coordinated. The customer sees validated aggregate totals without private references, notes or operator identity. Missing records do not prove nonpayment, unconfirmed shipping suppresses a final balance, and cancellation requires settlement review. This records completed external movements; it does not transfer funds or verify a provider.
