# Contact request recovery

The custom-print and general-contact forms retain an uncertain submission independently of the editable form. Reloading the page does not send a request. A customer can explicitly retry the saved request even when the current draft is different or invalid, without silently creating a new request identity.

## Customer workflow

- A failed or unconfirmed response exposes **إعادة محاولة الفكرة السابقة** or **إعادة محاولة الرسالة السابقة**, with the saved name/contact and request description. The action resends the original body and idempotency key. It can recover an existing receipt or create the original request once if the first attempt never arrived; the copy does not promise that a record already exists.
- Normal submission stays blocked while that endpoint has an unresolved attempt. Custom requests and general messages remain independent. There is no automatic retry, reset, or POST during page restoration.
- A successful response shows the real request/message reference and the captured submitted details. Custom-request WhatsApp follow-up uses that saved request and reference, including its original dimensions. It never constructs a message from newer form edits.
- Current drafts are compared when the response arrives. If different, the receipt explains that the edits remain available; **الرجوع لمسودة الفكرة المحفوظة** or **الرجوع لمسودة الرسالة المحفوظة** restores the edited form. An unchanged successful form can be reset for an explicitly new request. Completed receipt state also survives an ordinary reload within the same tab session.

The replay buttons are outside the form and its disabled fieldset. Their stable headings are `#custom-pending` and `#message-pending`; the existing receipt headings remain `#custom-result` and `#message-result`. Loading disables concurrent submission and mode switching. Receipt and explicit pending transitions focus their rendered heading. While a saved request is pending, the new-form validation summary is suppressed: an invalid edited draft does not need correcting before exact replay. Individual field feedback and recovery guidance remain available.

## Request and storage rules

The typed wrappers use `PublicRequestEndpoint`, `PendingPublicRequest<TBody>` and `RequestSubmissionService`. Pending bodies are immutable snapshots; reading one for display does not mutate the stored copy. The service accepts a receipt only when `success` is true and its ID and endpoint-specific reference are nonempty.

| Outcome                                                                 | Result                                                                                                                 |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| First, certainly rejected HTTP 422                                      | Release that still-current attempt; keep the form for correction and a new key.                                        |
| Network uncertainty, malformed acknowledgement, or a subsequent 409/422 | Keep the original key/body. Edited submission cannot replace it.                                                       |
| Changed body under an unresolved key                                    | Local `requestDetails` conflict without HTTP; the backend also rejects bound changed/malformed bodies with that field. |
| New attempt cannot be durably stored                                    | `requestStorage` failure before any POST; the UI explicitly says the request was not sent.                             |
| Saved pending data cannot be read safely                                | Block new sending and replay, retain the stored record, and show direct-contact guidance.                              |

There is no terminal absence proof for these inquiry endpoints. A generic rejection after uncertainty cannot establish that the original request was never saved.

Drafts and completed receipt snapshots use bounded, versioned `sessionStorage` state at `3d-otaku:contact-page`. Only the client reads/writes it, and restored form/receipt/pending UI appears after `afterNextRender` so it does not replace the server-rendered form before hydration. The request service separately stores one recovery record per endpoint. No idempotency key is rendered or included in WhatsApp links.

An actual page-state read/write exception raises a specific warning: current edits remain in the page but may not survive reload. The normal persistence note is suppressed while this warning is active, and only a successful page-state write clears it. Recovery is limited to the current browser tab session; closing it or manually clearing browser storage removes this local recovery path.
